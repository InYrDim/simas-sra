# Define the non-admin Tenant account lifecycle

Type: grilling
Status: resolved
Blocked by: 05

## Question

How does a School Admin create or invite non-admin Tenant accounts, link them to optional Warga Sekolah profiles, deliver and recover credentials, deactivate or reactivate access, and hand the resulting eligible account into the role-assignment workflow without crossing Provider-owned School Admin boundaries?

## Answer

### Boundary and account model

A School Admin may manage only **non-admin Akun Pengguna** whose authoritative `tenantId` equals the actor's verified Tenant. The server derives both Tenant IDs from authenticated and persisted data and rejects any target that is a Provider Admin, applicant-only identity, School Admin, cross-Tenant account, or identity with multiple/invalid central identity paths. A Tenant action can never set `tenantRole = school-admin`, change account ownership to another Tenant, attach Provider identity, or convert an existing identity path. Provider Admin remains the sole creator, credential resetter, deactivator, and reactivator of every School Admin.

These non-admin lifecycle operations use issue 13's exact reserved target keys and are all `school-admin-only`: `tenant.accounts.create` for creating the pending ordinary account record; `tenant.accounts.invite` for issuing its first invitation/activation ceremony; `tenant.accounts.link` and `tenant.accounts.unlink` for changing the optional Warga Sekolah link; `tenant.accounts.resend` for idempotently redelivering the same still-valid invitation under issue 10's policy; `tenant.accounts.reissue` for revoking/replacing lapsed, revoked, or otherwise unusable activation material; `tenant.accounts.deactivate` and `tenant.accounts.reactivate` for account access lifecycle transitions; and `tenant.accounts.initiate-recovery` for School-Admin initiation of the approved recovery flow. They are effective only through Provider-owned School Admin system policy, absent from custom-role selection, rejected in custom-role writes, and never delegable through a custom Role Tenant.

Issue 13's admission contract is authoritative: each reserved key remains unknown to runtime and fails closed until the same release ships its real endpoint or command, direct centralized evaluator enforcement, in-transaction authorization/state revalidation, required audit and denial/concealment behavior, and positive, negative, cross-Tenant, and concurrency tests. Documentation or registry naming alone grants no authority. User-owned authentication ceremonies remain outside Tenant RBAC: sign-in/out, changing one's own password, completing invitation/activation, email verification, requesting or consuming ordinary forgot-password recovery, MFA/passkey ceremonies, and session management continue to be governed by the authentication protocol, possession/reauthentication, token state, and abuse controls. The reserved School Admin keys may initiate eligible same-Tenant lifecycle ceremonies but never consume them, choose credentials, read secrets or hashes, or bypass Better Auth.

Account authority must not be inferred from Profil Guru, Profil Staf, Profil Siswa, names, or the legacy singular `user.tenantRole` values. The target model gives a non-admin Tenant membership an explicit lifecycle `pending-activation | active | inactive`, a monotonic `version`, activation timestamps, and an optional one-to-one same-Tenant `schoolPersonId`; Role Tenant assignments remain the only source of business permissions. Account lifecycle and Warga Sekolah/profile lifecycle are deliberately independent.

Use soft lifecycle transitions, not user deletion. Authentication and every Tenant authorization check fail closed unless the membership is `active`, the Tenant itself is operational, and required activation is complete. A `pending-activation` account may be handed to the assignment workflow and receive assignments, but cannot authenticate into Tenant features until activation; an `inactive` account cannot receive new assignments, as fixed by issue 05.

### Create, invite, and link

The account directory offers one flow with two entry points:

1. **From a Warga Sekolah record:** preselect that same-Tenant, non-archived person and use its name/email as editable suggestions.
2. **From the account directory:** enter account name and login email, then optionally search and select one same-Tenant, non-archived Warga Sekolah record.

Creation is always server-side and atomic. It normalizes the login email with the authentication library's canonical rules, reauthorizes the actor, locks/rechecks the selected person and identity candidates, creates exactly one non-admin Tenant membership in `pending-activation`, creates the credential/activation record, optionally writes the same-Tenant one-to-one link, and appends audit. It creates no profile, derives no role from a profile, and starts with zero roles unless a later role-assignment transaction succeeds.

**Invite is the default delivery mode** when a verified transactional-email channel exists: issue a cryptographically random, single-use, short-lived activation token stored only as a hash, bind it to user, Tenant, purpose and expiry, invalidate older invitations, and send a Tenant-branded HTTPS link to the login email. The link lets the recipient set a password; it does not expose whether other identities exist and does not carry role or Tenant authority in client-controlled claims.

Invitation delivery follows issue 10's explicit two-operation contract. **Resend** is idempotent redelivery of the same still-valid activation material for the same invitation/case and records `tenant_account.invitation_resent`; it does not extend expiry, change the token digest, increment account version, revoke sessions, or create a second invitation. If the material is expired, consumed, unavailable for safe redelivery, or otherwise no longer valid, resend is rejected. **Reissue** is a security mutation that locks current state, revokes and replaces all prior activation material, preserves the account identity, starts a new bounded expiry/attempt context, and records `tenant_account.activation_reissued`. Only reissue may produce a new link/token or temporary credential. Delivery retries use an idempotent outbox/delivery key so retries cannot accidentally become reissues or duplicate audit events.

**Create with temporary credential** is the controlled fallback when email delivery is unavailable. Reuse the existing secure pattern: generate at least 192 bits with a CSPRNG, store only the Better Auth password hash, require password change, display the plaintext once in the successful response, and revoke the credential when reissued. The School Admin must deliver it through a separate authenticated channel; it must never appear in email together with the username, logs, audit payloads, URLs, exports, notifications, or later reads. Do not allow a School Admin to choose or retrieve a user's password.

Linking is optional and requires explicit confirmation. A `schoolPerson` may link to at most one account and an account to at most one `schoolPerson`, enforced by same-Tenant composite foreign keys and uniqueness constraints. Linking or unlinking requires account/profile versions, a reason, and an impact preview. It never copies sensitive person identifiers into authentication data, changes either lifecycle, or grants/revokes access. Archiving or ending a Guru/Staf/Siswa profile only warns when a linked account remains active; it must not silently deactivate that account. Conversely, deactivating an account must not archive its person or profiles.

### Collision handling and privacy

The global login email is an identity key, not a Tenant-local attribute. Before creation, the server resolves the canonical email and selected person under transaction and database uniqueness constraints:

- If the email is unused, create the new identity.
- If it belongs to an existing non-admin membership in the same Tenant, return the existing account as an idempotent match and offer link/resend/reactivate as permitted; never create a duplicate.
- If it belongs to a School Admin, Provider Admin, applicant identity, another Tenant, or an invalid/multiple identity path, do not merge, rehome, or reveal that fact. Return the same generic **Tidak dapat membuat atau mengundang akun dengan data tersebut** result and route remediation to an authorized support process.
- If the selected Warga Sekolah is already linked, return a same-Tenant conflict naming only the account information the actor is authorized to view. Possible person duplicates use the existing explicit candidate-selection/confirm-distinct pattern, but only within the actor's Tenant; NIK, NIP, birth data, phone, and cross-Tenant matches are never exposed in account search or collision messages.

Public invite, login, and recovery responses are enumeration-resistant and rate-limited by normalized identity plus IP/device signals. Audit and operational logs store user IDs and redacted delivery metadata, not tokens, passwords, full sensitive identifiers, or raw recovery answers.

### Activation and credential recovery

Activation is complete only when the invitation/temporary credential is valid, the recipient successfully establishes a new password meeting the central password policy, any required email verification succeeds, and the transaction changes membership from `pending-activation` to `active`. First authentication alone is not activation: the current session-create hook may record `firstAuthenticatedAt`, but `passwordChangeRequired` continues to block Tenant access. Password replacement, token consumption, activation state/version update, audit append, and revocation of every other session occur atomically. The activation token/temporary credential is one-time; stale, expired, replayed, or superseded material produces the same generic failure.

Before first successful activation, School Admin may **resend an invitation** or **reissue activation material** after confirmation and rate limiting. Resend performs only idempotent redelivery of the same still-valid invitation and records delivery attempt metadata plus `tenant_account.invitation_resent`; it never reveals a token in the UI or revokes/replaces material. Reissue locks the activation row, invalidates all prior invitation/temporary-credential material, revokes all sessions, creates one replacement, records issue count/time/channel plus `tenant_account.activation_reissued`, and reveals a replacement temporary credential only once when that delivery mode is used. This generalizes the existing Provider reissue mechanics but authorizes only same-Tenant non-admin targets; the Provider-only School Admin reset action remains unchanged and inaccessible.

After activation, School Admin can no longer issue or view a credential. Recovery is user-controlled through Better Auth's password-reset flow: a single-use, purpose-bound, short-lived token is sent only through the verified channel; responses stay generic; successful reset revokes all sessions and is audited. Until the server-side reset-token issuer and mail callback are configured and tested, the existing forgot-password page must not be represented as operational; use Provider/support-assisted identity verification that triggers the same reset-token mechanism, never a School-Admin-chosen password. School Admin may initiate a generic recovery message for a same-Tenant non-admin account but receives no token and no confirmation that the recipient used it.

### Deactivate and reactivate

Deactivation requires an `active` or `pending-activation` same-Tenant non-admin target, current account `version`, confirmation showing linked profile and effective-access impact, and a mandatory secret-free reason. In one locked transaction it reauthorizes actor and target, changes membership to `inactive`, increments version, invalidates pending invitations/recovery material, revokes all sessions, suspends all Role Tenant assignments, and appends lifecycle plus per-assignment audit under one correlation ID. It does not delete credentials, account history, person/profile data, or assignments. Enforcement observes deactivation on the next request and does not rely solely on session claims.

Reactivation requires an `inactive` same-Tenant non-admin target, expected version, reason, and a collision/identity integrity recheck. It never restores access silently. The confirmation must choose either (a) no roles or (b) an explicit subset of formerly suspended roles that satisfy current role status, same-Tenant ownership, `tenant-assignable` registry classification, known/non-deprecated permission keys, and a valid complete permission-dependency closure. Reactivation and that assignment decision commit atomically with one audit context; stale versions, draft/archived/removed/unknown roles or keys, broken dependencies, and School Admin roles fail closed. Provider feature entitlement is not restoration eligibility and does not remove an otherwise valid role from the selectable former set. Instead, the preview and resulting effective-access view retain the role and explicitly mark each entitlement-disabled permission **Tidak tersedia untuk Tenant**; those permissions remain unusable while the entitlement gate is disabled. A reactivated account with a valid established credential returns to `active`; if credential ownership cannot be safely established, it returns to `pending-activation` and receives a new invite/recovery ceremony rather than a School-Admin-set password.

Deactivation/reactivation is independent from employment or student status. The UI may warn when profile state and account state appear inconsistent, but only an explicit account lifecycle action changes authentication access.

### Assignment handoff

A successful create/invite response returns the stable `userId`, account lifecycle/version, optional linked-person summary, and a server-generated next action to **Atur Role Tenant**. The role editor reloads the account by `userId`; it never trusts email, person ID, role IDs, Tenant ID, eligibility, or status carried from the creation form. It applies issue 05 unchanged: School Admin is never assignable, assignments are atomic and additive, zero-role accounts are valid, inactive accounts reject new grants, and active access changes apply on the next request.

For `pending-activation`, role assignment is staging only: the UI states that roles will grant no usable access until activation. Activation does not alter the staged assignment set. The activation confirmation and first post-activation request evaluate current authoritative roles and entitlements, so revoked or archived roles never survive through stale invitation state.

### Concurrency, idempotency, audit, and UI states

Every create/invite/link/resend/reissue/deactivate/reactivate/recovery-initiation mutation accepts a single-use idempotency key and, for an existing account/person, expected versions. The database supplies canonical-email uniqueness, same-Tenant composite foreign keys, one-to-one link uniqueness, and one current activation state. Mutations run in transactions with row locks or compare-and-swap updates, repeat authorization and lifecycle/identity checks after locking, and translate uniqueness/version races into deterministic `already exists` or `conflict—reload` outcomes. No check-then-write result from the browser is authoritative.

Append-only audit records actor, target user, Tenant, operation, before/after lifecycle and version, link and assignment diffs, delivery channel (not destination secret), reason where required, timestamp, request/correlation ID, and success/failure category. Credential/token values and sensitive Warga Sekolah fields are excluded. Security telemetry separately records throttling, collision category, invalid/replayed activation, session revocation, and forbidden boundary attempts using redacted identifiers.

All account lifecycle surfaces explicitly inherit the **full loading, success, error, empty, stale, responsive, and accessibility contracts from issues 08 and 09**, not merely their loader requirement. This applies to every create/invite/link/unlink/resend/reissue/deactivate/reactivate/recovery dialog or sheet, the one-time credential reveal/acknowledgement screen, and initial/refresh/search/filter/pagination/empty/error states in the account directory.

Concretely, use semantic design-system controls and headings; programmatic dialog title/description; focus trap, visible focus, logical tab order, Escape only before submission, and focus restoration; initial destructive-dialog focus on a focusable heading/consequence summary rather than either action; full keyboard operation; text in addition to color/icons; labelled fields with `aria-describedby`; error summaries linked to fields and focused after failure; `role="alert"` for destructive/validation failures; polite live regions/`role="status"` for progress and success; reduced-motion loaders; 200% zoom/reflow without two-dimensional scrolling; `min-h-11` touch targets; narrow-screen list/card or sheet alternatives; and accessible names, table headers/captions, and status text. The one-time credential screen announces its heading without reading the secret automatically, provides a labelled keyboard-operable copy action and non-secret copy confirmation, does not place the secret in a live region, requires explicit acknowledgement before leaving, and cannot redisplay it after navigation.

Every asynchronous form disables only its own controls, prevents duplicate submission, and shows a visible spinner plus consequence-specific pending text (`Mengundang…`, `Membuat…`, `Menautkan…`, `Mengirim ulang…`, `Menerbitkan ulang…`, `Menonaktifkan…`, `Mengaktifkan kembali…`, or `Memulihkan…`). Directory initial loads use stable labelled skeletons; refresh/search/filter/pagination retains current rows with `aria-busy="true"`, announces **Memperbarui hasil…** and result counts without stealing focus, and prevents stale responses from replacing newer queries. Distinguish default empty, filtered empty, denied, not-found/non-enumerating, delivery failure, stale conflict, and unexpected/correlation-ID states. Preserve safe input and current rows on recoverable errors, keep dialogs open, and offer review/reload rather than overwriting stale state.

Invite and recovery success messages remain generic. Partial success is forbidden: if account, link, activation material, assignment suspension/restoration, or audit cannot commit, the entire lifecycle mutation rolls back; external email is dispatched from a transactional outbox only after commit. A post-commit delivery failure retains the safe pending account/invitation state, reports that no access was granted, and offers the idempotent resend operation rather than silently reissuing material.

### Evidence and implementation implications

- `db/schema.ts` currently makes `user.email` globally unique and stores Tenant ownership plus a singular `tenantRole`; this supports global collision detection but requires a dedicated non-admin membership status/version rather than overloading role strings.
- `schoolPerson.accountUserId` already has same-Tenant composite referential integrity and one-link-per-person uniqueness. Person/profile services initialize accounts as unlinked and warn, rather than cascade, when an archived Guru/Staf/Siswa has an active linked account. Preserve that separation and add the reciprocal one-account-per-person constraint if it is not guaranteed by the target membership model.
- `temporary-credential-activation.ts` uses CSPRNG-generated 24-byte base64url secrets, Better Auth hashing, row locking, mandatory password change, one-time display, and session revocation. Reuse these mechanics, but split authorization by target kind: its present principal and reset command are intentionally School-Admin/Provider-specific.
- `temporary-credential-activation-data.ts` locks activation rows with `FOR UPDATE`, conditionally marks first authentication, replaces hashed credentials, and revokes sessions transactionally. Extend the state model so first authentication cannot be mistaken for completed activation.
- `platform/auth.ts` records first authentication on session creation and exposes Tenant fields as non-input Better Auth fields. `central-identity.ts` rejects zero or multiple identity paths and routes `passwordChangeRequired` users to password change; retain those fail-closed properties for non-admin accounts.
- The forgot-password UI is enumeration-resistant and has a loader, but the inspected Better Auth server configuration only enables email/password and does not show a reset-token delivery callback. Recovery therefore remains an implementation prerequisite, not evidence of a working delivery channel.
- Existing Guru/Staf/Siswa services use same-Tenant transactions, expected versions, duplicate/link-required decisions, lifecycle history, reasoned archive/reactivate operations, and sensitive before/after audit. Reuse these concurrency and audit conventions without coupling profile lifecycle to account lifecycle.
- Issue 10 fixes `tenant_account.invitation_resent` as same-material redelivery and `tenant_account.activation_reissued` as revoke-and-replace; its event envelope, idempotency, retention, visibility, and secret-exclusion rules are authoritative here.
- Issue 13 reserves the exact `school-admin-only` lifecycle keys mapped above: `tenant.accounts.create`, `.invite`, `.link`, `.unlink`, `.resend`, `.reissue`, `.deactivate`, `.reactivate`, and `.initiate-recovery`. Its bundled admission rule is authoritative: every key remains runtime-unknown and fail-closed until endpoint/command, centralized enforcement, transactional revalidation/audit, denial/concealment behavior, and positive/negative/cross-Tenant/concurrency tests ship together; user-owned authentication ceremonies remain outside Tenant RBAC.
- Issues 08 and 09 supply the complete loading, stale/error, responsive, keyboard, focus, live-region, reduced-motion, zoom/reflow, and destructive-dialog contracts inherited above.
- The current required-password page does not expose a pending/loading state while its server action runs. The non-admin implementation must add one, and the shared activation UI should be brought to the inherited issues 08/09 contract when implemented.
